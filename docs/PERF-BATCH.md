# Global per-tick batching (`mc.server_tick_batched`)

An opt-in alternative entry point for the whole tick that sends the gateway **byte-identical output** to `mc.server_tick()` with fewer statements, almost no plan-invalidating
statements in the tick and fewer copies of every frame.  Nothing existing was edited: everything is in new files (`sql/380`-`383`, `sql/389`, `sql/optional/batch_grid_vis.sql`), the tests are `tests/sql/385`-`388`
and the benchmarks are in `tests/bench/batch/`.  Gateway contract unchanged: frames into `net.inbox`, `select mc.server_tick_batched()`, `net.drain_outbox()` out.

## Result in one paragraph

On this machine (4 shared cores, PostgreSQL 16, `jit=off`), at 500 players spread over 100x100 chunks the batched tick costs **40% less CPU per tick** than the baseline when all players
move (84 -> 51 ms CPU; -30% to -40% in four independent measurements), **45% less** when 20% move, and an idle server with no players drops from 16.6 to 2.6 ms per tick.
Statements per tick roughly halve (2,199 -> 1,150), WAL halves (170 -> 87 KB per tick) and mc.player's updates become almost all HOT (94% -> 99%).  **It does not make a crowded or a 2,000-player tick
fit in 50 ms** (229 and 380 ms): there the cost is delivering 80k-160k viewer-pair move packets, which batching does not remove, and the saving shrinks to 7-17%.
The saving comes from three things that reinforce each other, each worth 10-18 ms in the ablation: **no plan invalidation in the tick** (planning 12-14 -> 7-8 ms), **half the data movement** (one hop for
every inbound frame, one update per mover, packets built once), and **not running phases that have nothing to do**.  A fourth idea I expected to pay (`out`, one outbox row per connection) did not, and is opt-in.

## What it is

`mc.server_tick_batched()` runs the baseline's order of work (ingest -> game tick -> block actions/events -> chunk streaming -> kicks and leavers -> drain) with these components, each
switchable with `mc.batch_flags` (`alter database X set mc.batch_flags = 'in,mv'`; unset or `all` = **in, mv, vis, ch, skip**; `none` = the baseline's phases orchestrated by the new function; `out`, `ref` and `grid` are opt-in):

| flag | file | what it does |
|---|---|---|
| `in` | 381 | one statement claims `net.inbox` and routes every frame: hot play packets straight to `mc.play_in_work` (the baseline copied each frame inbox -> batch -> play_inbox -> play_in -> play_in_work), everything else to the per-connection loop |
| `mv` | 382 | movement as ONE statement: decode, rule violations, teleport confirmations, last position per connection, moved-too-quickly correction, apply, broadcast; **one update per player** (the baseline updates a mover twice); one ordered insert into `mc.play_out` (kick packets, then corrections, then the fan-out) |
| `vis` | 381 | visibility refresh as one CTE statement driven from the primary-key/target indexes by an array of the dirty players; the `add_entity` packet is built once per target; no temp tables, no ANALYZE |
| `ch` | 380 | chunk streaming for every player that crossed a border as ONE ordered insert; packets come from a join with the packet cache (per-row primary-key probes), a stale or missing chunk goes through `mc.chunk_packet_generate` |
| `out` (opt-in) | 380 | `mc.play_out` -> `net.outbox` in one statement, one row per connection (the baseline: `_drain` temp table, then one outbox row per frame); **net negative, see variant 3** |
| `skip` | 389 | phases with nothing to do are not run: chat, creative slots, block actions, block events, kicks/leavers, visibility when nobody changed chunk; no `TRUNCATE` in the tick except the one the default drain still causes (see below) |
| `ref` (opt-in) | 383 | chunk packets travel as references to the cache and are expanded by `net.drain_outbox_ref()`; **not recommended, see variant 8** |
| `grid` (opt-in) | optional | visibility neighbour search through an index on `(chunk_x, chunk_z)`; see variant 4 |

The rare, complicated paths are **not** re-implemented: the per-connection state machine (handshake, login, configuration, join), chat and commands, creative slots, block actions and their
broadcast, keep-alive, leaving, and the world functions all still call the existing functions, so improvements made to them elsewhere flow in unchanged.

## Proof that the bytes are the same

| test | what it proves |
|---|---|
| `385_batch_replay`, `386_batch_behaviour` (generated by `gen_tests.sh` from 410 and 420 by replacing `mc.server_tick()`) | the scenarios that are compared with real vanilla 26.3 traffic (65 clientbound packets of a recorded join, two players, chat, leave, block actions, chunk streaming, kicks, compression) pass through the batched tick: 75 + 66 checks |
| `387_batch_diff_moves` | `mc.moves_batched` vs `mc.apply_player_moves` on **300 random states and scripts** (1,122 kicks, 501 corrections, NaN/infinite values, malformed packets, clamping, confirmations, offline players): identical bytes per connection, identical final state of every player, identical kicks and counts |
| `388_batch_diff_ticks` Part B | whole ticks, **120 random 4-tick trials with at most one misbehaving connection per tick**: identical drain bytes in the same order, identical players, visibility, connections, errors; includes cold-path frames (unknown ids, chunk batches, keep-alive answers), chunk-border crossings and unknown connections |
| Part C | the same with several connections closing in one tick (what is defined is compared: survivors' frames as sets, which connections close, all state) |
| Parts D, E, F | the opt-in `ref` (80 + 80 trials), `grid` (60) and `out` (60) flags |

All of the baseline's 724 checks still pass in the same database (875 in 20 test files with the new ones).  **What the differential tests cannot say**: they compare with the baseline, not with vanilla, outside the
scenarios 385/386 replay; chat, commands, block actions and the join are untouched code paths; **`tests/e2e` (real TCP against a vanilla server) was not run** (fixed ports shared with other workers).

Two places where the baseline is not deterministic, found by the differential test (neither is a bug of the batched tick):

* **Several connections closing in the same tick** are processed by `for r in select ... from net.conn where closing` in physical row order, which the baseline's own `UPDATE`s permute.
  The connection that leaves first is not told about the later leavers, so even the *set* of frames sent to a closing connection depends on it.  The batched tick has the same loop; adding `ORDER BY c.conn_id` to it (in both) would make it deterministic.
* `mc.pkt_remove_entities(array_agg(target_eid))` lists entities in scan order; the test compares those id lists sorted.

## Method

* `tests/bench/batch/ab.sh`: a fresh `ibench.setup` per run, **deterministic input** (a pure function of connection, tick and position, so both implementations see identical traffic), implementations
  **interleaved with a rotating order** (no implementation always runs first or last; load from other processes drifted during a round), medians over rounds.  The first 20 ticks are warm-up.
  A first ablation without rotation and with wall-clock time only was discarded: it was dominated by ordering and noise.
* **CPU time** is the backend's own on-CPU time from `/proc/self/schedstat` (the tick function only), with the run-queue wait reported separately (it was below 1 ms in the runs below).
  The kernel updates that counter in 4 ms steps, so single ticks are quantised; averages over 40+ ticks are not.  Wall times are reported where the tail matters.
* Statements, planning time, WAL, rows written and HOT updates come from `pg_stat_statements` (with `track = all`, `track_planning = on`), `pg_current_wal_lsn` and `pg_stat_user_tables`.
* The cluster is the dev cluster of `tools/pg-dev.sh` (`fsync=off`, `synchronous_commit=off`), database with a **warm world** (16,641 chunks generated and cached).  Three other workers were loading the
  4 CPUs the whole time (load average 2-5): absolute numbers drift between sweeps (the baseline's 500-sparse CPU was 83.0, 69.6, 79.1 and 84.3 ms in four sweeps); the **ratios** are steadier (-30% to -40%).
  Differences below about 10% between single configurations are noise.  Crowded results varied most (-3% to -33% across five measurements; the sweep says -7%).
* Scenarios: *dither* = every moving player takes a +-0.2 block step (players re-cross chunk borders constantly, which stresses chunk streaming and visibility), *walk* = straight at 0.22 blocks per
  tick; *sparse* = 100x100 chunks (about 19 viewers per player at 500 players), *crowded* = 30x30 chunks (about 160 viewers per player).

### Where the gain comes from (leave-one-out, 500 sparse, all moving)

CPU ms per tick with each component removed from `all` (higher = that component matters more):

| configuration | CPU ms/tick (p99) | change vs all six |
|---|---|---|
| base (the baseline tick) | 77.2 (115) | |
| all six components (`in,mv,vis,ch,out,skip`; this run's `all` included `out`) | 49.1 (69) | |
| without `in` (ingest fused) | 67.4 (97) | +18.3 ms |
| without `skip` (skip empty phases) | 66.3 (98) | +17.2 ms |
| without `vis` (visibility) | 61.9 (95) | +12.7 ms |
| without `mv` (movement fused) | 61.0 (94) | +11.9 ms |
| without `ch` (chunk streaming) | 58.7 (80) | +9.6 ms |
| without `out` (one-row drain) | 44.3 (65) | -4.9 ms |

Every component except `out` is worth 10-18 ms here (more than their sum, because plan invalidation by any remaining baseline phase hurts every statement).  **`out` is the exception: removing it makes the tick about 5 ms cheaper**; its saving (the gateway's drain) is smaller than its cost.  Three independent measurements agree (this one, an earlier ablation with the first visibility version, and a dedicated comparison over 6 rounds: tick CPU 47.9 ms without `out`, 53.0 ms with; gateway drain 4.1 vs 2.4 ms; net +3.5 ms worse with it), so **`out` is not part of `all`** (opt-in).

## The variants, one by one

1. **Stage tables (temp / unlogged, `ON COMMIT DELETE`, truncate)**: *not built, and measured the other way round*.  The baseline already is that design and its stage tables are what hurts: `TRUNCATE`, `ANALYZE` and
   `ON COMMIT DELETE ROWS` temp tables invalidate the cached plan of every statement that touches them, so the baseline **re-plans about 110 statements every tick: 12-14 ms of planning of 67-84 ms of CPU**
   (`plan ms/tick` column).  The batched tick uses data-modifying CTEs and `DELETE` only: 7-8 ms.  Without the `skip` guards (which avoid the remaining `TRUNCATE`s and the phases themselves) it is 12.5 ms and the tick
   costs 17 ms more (leave-one-out).  An idle tick with no players: **16.6 -> 2.6 ms**, 123 -> 65 statements; 500 idle players: 27.3 -> 10.9 ms.
2. **Packet-once fan-out**: the baseline already builds each move packet once per mover (`MATERIALIZED`), kept.  I applied it to visibility too (`add_entity` once per target instead of once per new viewer-target pair,
   about 12,000 pairs a tick when crowded); in single runs this did not give a reliable gain: crowded visibility measured 39-47 ms in both implementations (the final phase table shows 39 ms baseline and 46 ms batched).
   Packets built vs delivered per tick, all players moving: 500 built / 9,706 delivered (sparse 500, **19x**), 500 / 79,364 (crowded, **159x**), 2,000 / 156,494 (sparse 2,000, **78x**): delivery, not building, is
   the cost at scale.
3. **One blob per connection**: the `out` component makes the outbox one row per connection per tick.  The gateway-facing `net.drain_outbox()` gets cheaper (4.1 -> 2.4 ms per tick at 500 players) and rows deleted per tick fall
   (5,654 -> 5,085), **but the tick pays more than the drain saves**: concatenating the frames into a blob (`string_agg` over about 1.3 MB per tick, then inserting the blob) costs about 5 ms of tick CPU more than the baseline's
   many small inserts; net +3.5 ms (a dedicated 6-round comparison, and two ablations, agree).  So it is opt-in.  Ordering holds either way (connection-layer rows first, then the game's, each in generation order; with compression
   enabled frames are re-framed per connection as before; differential Part F).  Also tried and rejected: `SET STORAGE EXTERNAL` on the queue tables' `bytea` columns, on the theory that Postgres wastes time trying to compress
   transient frames: no measurable change (77.8 / 47.4 / 44.1 ms against 77.2 / 49.1 / 44.3 ms).
4. **Interest management**: the visibility join compares each player that crossed a border with every online player (dirty x online: 400,000 distance checks at 2,000 players with 100 crossing, 15,598 wanted pairs of which
   710 new).  `batch_grid_vis.sql` (opt-in, an index on `(chunk_x, chunk_z)`, which changes only when a player crosses a border so other updates stay HOT) turns it into a range lookup: in the final sweep CPU 229 -> 220 ms crowded and 380 -> 385 ms at 2,000 players (no gain there; a separate earlier comparison showed -4%), i.e. within noise, so not recommended.  The rewrite that
   matters more was making the `mc.visible` access index-driven from an array of dirty ids: the first version (an `OR` of two `IN` subqueries) scanned all of `mc.visible` and was 20 ms *slower* than the baseline when crowded.
5. **Arrays / columnar batching**: not pursued.  The profile did not show a phase whose cost an array formulation would remove; rows are not the bottleneck at 500 players.
6. **Cross-tick amortisation / dirty flags**: the `skip` guards and the single update per mover.  `mc.player` updates per tick 2,272 -> 1,522, HOT 95% -> 99%, WAL 160 -> 85 KB per tick.  No change in what is sent, so nothing is
   listed as a deviation.  Not adopted because it would change bytes: coalescing movement updates for distant viewers (the 80k-160k pair deliveries are exactly what vanilla sends).
7. **Transaction shape**: one transaction per tick (what the PL/Python gateway does) against separate commits for input, tick and drain (what `tests/bench/integration` does): **the baseline gets 21% cheaper in one
   transaction (84 -> 67 ms CPU)** because its `ON COMMIT DELETE ROWS` temp tables are truncated, and their statements invalidated, at every commit, and split mode commits three times a tick; the batched tick gains 10%
   (51 -> 46 ms).  So the earlier integration benchmark overstated the baseline's cost relative to how the dev gateway really runs it, and the batched tick's advantage in the gateway's own transaction shape is -32% (scenario `s9`).
   Plan caching: the saving above *is* plan caching (no invalidation); I did not separately test `plan_cache_mode = force_generic_plan` or prepared statements.  About 3.6 ms of planning per tick remain in the batched tick
   from `proto.frame` (`sql/315`), see findings.
8. **Reference outbox / zero-copy fan-out (`ref`)**: implemented (`sql/383`), byte-identical (differential Part D, and the join burst's md5 equals the baseline's).  Result, **against the working hypothesis**: the cost in a join is *not*
   copying cached packets; it is calling a function per chunk.  Chunk burst of a join (warm cache, CPU ms, median of 12):

   | view distance | chunks | one function call per chunk (`net.send_chunks`, the baseline) | one set-based join, bytes (`setbytes`) | by reference (`ref`) | same bytes? |
   |---|---|---|---|---|---|
   | 9 | 441 | 283.27 ms | 15.91 ms | 19.55 ms | yes (md5 of everything drained is identical) |
   | 10 | 529 | 333.09 ms | 16.01 ms | 23.92 ms | yes (md5 of everything drained is identical) |

   Replacing the per-chunk function calls with one set-based lookup (`setbytes`, still copying the bytes) gives the whole 15-20x; references are not faster than that.  In the 500-player tick the reference outbox made no
   difference in the final sweep (45.9 ms with `ref`, 46.0 without) and adds about 0.5 ms to the gateway's drain; an earlier sweep, whose `all` still included `out`, showed -4 to -12 ms, which was `ref` bypassing `out`'s cost, not the
   references.  Semantics defined for a reference whose cache entry was replaced between enqueue and drain: the current packet is sent (never older, never torn; see `sql/383`).
   **Recommendation: do not adopt `ref`; adopt the set-based lookup** (`ch`, and the same join in `net.send_chunks`, which this work did not change because it is an existing file).  The hypothesis that copying the ~7 KB packets
   dominates is not supported by these measurements; the per-chunk function-call overhead does.
9. **Cache storage**: `mc.chunk_cache.packet` as stored by default is already tiny, because pglz compresses a 7,262-byte flat-chunk packet to 184 bytes (**39x**); reads pay a decompression but it is not the bottleneck.
   Measured on copies of the table (16,641 rows):

   | storage | stored bytes per packet (raw 7,262) | table + TOAST | join-sized fan-out, 20 x 529 chunks (CPU ms, median of 15) |
   |---|---|---|---|
   | default | 184 | 5032 kB | 35.94 (measured twice: 35.94 and 31.88) |
   | external | 7262 | 134 MB | 49.65 |
   | main | 184 | 5032 kB | 24.00 |

   `EXTERNAL` costs **27x the disk (134 MB against 5.0 MB)** and reads slower; `MAIN` is the same as the default.  **Keep the default.**  (Real terrain compresses far less than a flat world, so re-measure with real chunks;
   the 4 ms resolution of the CPU counter hides the small-read differences, the join-sized fan-out shows them.)
10. **Chunk streaming as one set-based statement**: that is the `ch` component (one ordered insert for all players that crossed a border: ring difference from a generated offsets series, nearest first with a stable
    tie-break `(d, x, z)`, forgets ordered `(z, x)`, same frames per connection as `net.stream_chunks`).  Tested by differential Parts B-E (several trials with chunk streaming for 14 players over 4 ticks) and by the vanilla-verified
    scenarios 385/386.  Not available to me: `tests/sql/430_chunk_queue.sql` and the asynchronous chunk queue, which live on the chunks worker's branch (my tree branched before it).  Phase effect: chunks 10.8 -> 5.8 ms (500 sparse),
    28.9 -> 16.8 (2,000).

## Findings for the other workers

* **Plan invalidation is the biggest single cost in the baseline tick** (about 13 ms of planning per tick): `TRUNCATE mc.play_in_work, net.batch, net.play_inbox, mc.kick, mc.pending_ack, mc.block_actor`, `ANALYZE _vis_on`/`_mv`, and temp
  tables created `ON COMMIT DELETE ROWS` all invalidate plans.  Replacing them with `DELETE` guarded by `EXISTS` fixes most of it.  `pg_stat_statements.track_planning = on` shows it immediately.
* **`proto.frame` (`sql/315_game_fast.sql`) is not inlined** whenever its `body` argument contains a subquery (it references `body` twice, so the planner refuses to inline a multi-referenced subplan): about 37 executions per
  tick through the function-call path, re-planned 14 times a tick, **3.6 ms of planning per tick**.  A cheap fix is to build the frame length in a `LATERAL` at the call site, or to give the callers a single-reference form.
* **CTE statements have no statistics**: the planner assumed hundreds of rows for a 575-row CTE and hash-joined the whole of `mc.chunk` and `mc.chunk_cache` (68 ms instead of 3 ms).  Correlated scalar subselects
  (`(select ... where pk = outer.col)`) are planned as per-row index probes regardless; used throughout 380-383.
* **A volatile call or a subquery argument blocks inlining** (known); an `OR` of two `IN (subquery)` over a large table is planned as a sequential scan: drive it from arrays and indexes.
* **The leaver loop and the baseline's `array_agg` orders are undefined** (above).

## Merging with the other work

* Overlap with TICK-PERF: the functions the batched tick replaces in its hot path are `net.process` (195), `mc.tick` and `mc.apply_player_moves` (360, 340), `mc.refresh_visibility` (330), `net.stream_chunks` (410) and the
  drain in `mc.server_tick` (420).  The batched tick **calls unchanged** `apply_misc_input`, `apply_chat`, `apply_block_actions`, `broadcast_block_events`, `keepalive_due`, `on_leave`, `net.handle`, `net.fail`, `mc.pkt_*`: their
  improvements apply to both entry points automatically.  If TICK-PERF changes the semantics of one of the *replaced* functions, `387`/`388` fail, which is the intended merge gate; if it only speeds them up, the two entry points
  can be compared with `tests/bench/batch/ab.sh "base batched:all"` after the merge.
* Overlap with CHUNKS-PERF: `net.stream_chunks_batched` and `mc.chunk_packet_generate` duplicate the idea of an asynchronous generation path on a smaller scale (generate on the tick for a missing chunk); once the chunk
  queue exists, the `ch` fallback should enqueue instead of generating.
* **Recommendation: adopt `mc.server_tick_batched` as the default entry point after `tests/e2e` has been run against it** (the byte-for-byte comparison with a real vanilla server is the one proof I could not run), keeping the
  baseline functions for reference and as the oracle of the differential tests.  `ref` and `grid` stay optional.

## What this does not show

* **One plan-invalidating statement is left in the default tick**: the drain into `net.outbox` still uses the baseline's `_drain` temp table (`ON COMMIT DELETE ROWS`, truncated at every commit), so the 2-3 statements that
  touch it are re-planned every tick.  A one-statement drain that keeps one outbox row per frame (like the baseline) but needs no temp table is the obvious next step; I did not build it, so the planning column above (7-8 ms) still
  contains that cost.

* No real client, no gateway, no TCP: the harness drives `net.inbox`/`net.drain_outbox` in a loop.
* The cold paths (join, login, chat, commands, block actions) are the baseline's; a login storm or a join into an unexplored world is as slow as before.  A join's chunk burst is 15-20x cheaper through a set-based lookup
  (variant 8), but `net.send_chunks` itself was not modified.
* Real vanilla traffic differs from this synthetic walk; sparse/crowded/2,000 bracket it but do not replace a recording.
* The ratios held across four sweeps, the absolute numbers did not.
