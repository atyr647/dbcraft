# Tcl as the gateway language: measurements with tcl-aot

Question: is Tcl 8.6.14 compiled with [tcl-aot](https://github.com/atyr647/tcl-aot) viable as the tiny dbcraft gateway (sockets, VarInt framing, packet
decode/encode, AES-CFB8, zlib), compared with plain interpreted Tcl and with native Rust?

**Short answer: no, not for the "match Purpur" target.** tcl-aot helps a lot on pure integer loops (11x) and 3.6x on tcllib's AES, but gateway work is mostly
`binary scan` / `binary format` / list and string commands, where it changes almost nothing (1.03x to 1.13x), and the remaining gap to Rust on those rows is 58x to 530x.
Tcl 8.6 also cannot hold more than about 1000 sockets in one process (see "Sockets"). Details, caveats and what would change the answer are below.

## Setup

Linux x86-64, 4 cores, Tcl 8.6.14 built by `make tcl shell` in the tcl-aot checkout (static libtcl, default `configure`, so threaded), tcllib 1.21 from apt,
Rust 1.97 release build (`opt-level=3`, `lto`) using std only (zlib through FFI to `libz`; AES written by hand: software and `std::arch` AES-NI).

All three implementations read the **same input files** (`tests/bench/tcl/data/`, generated by `gen_data.py` with a fixed seed) and print `RESULT` lines that
are compared with an oracle computed in Python (and `openssl enc -aes-128-cfb8` for AES). Every RESULT line matched in all three, so the work compared is the
same work.

Files (all under `tests/bench/tcl/`): `gen_data.py` (inputs and oracle), `gw_procs.tcl` (the Tcl procs; one file, translated by tcl-aot **and** sourced at run
time so compiled bodies attach), `run.tcl` (driver), `rust/src/main.rs` (baseline), `run_all.sh`, `summarize.py`, `sock_server.tcl`, `sock_client.py`.

### Commands

```
# build tcl-aot's Tcl and translator shell (55 s on this machine)
cd /home/user/atyr647/tcl-aot && make tcl shell
apt-get install -y tcllib                       # pure-Tcl AES lives in tcllib's `aes` package
# everything else (translate, build, 2 rounds of interp / aot / rust, summary):
export TCL_LIBRARY=/home/user/atyr647/tcl-aot/build/tcl8.6.14/library    # the static shell needs Tcl's library dir
tests/bench/tcl/run_all.sh                      # about 2 minutes; AES_BYTES=65536 by default; REPS=5 (Rust 10); best of all runs is reported

# what run_all.sh does for the tcl-aot part:
. tools/env.sh
$TCLSH src/translate.tcl tests/bench/tcl/gw_procs.tcl out/gw.c Gw                 # 1.9 s
cc -O2 -w -DMODULE=Gw $TBC_INC tools/module-shell.c out/gw.c $TBC_LIBS -o out/gwshell   # 34 s (2.7 MB of C)
out/gwshell run.tcl                    # interpreter alone (same binary, module not loaded)
COMPILED=1 out/gwshell run.tcl         # `load {} Gw` first, then the procs are defined and compiled bodies attach
```

The interpreter baseline and the compiled run use the **same executable and the same libtcl**; only `load {} Gw` differs.

## Results

#### Correctness (every RESULT line vs the Python/openssl oracle)

- interp: all RESULT lines match (9 distinct lines)
- aot: all RESULT lines match (9 distinct lines)
- rust: all RESULT lines match (11 distinct lines)

Notes on the table:

* "ops" are VarInts, frames, decodes, or packets delivered; MB/s is input or output bytes per second. Best of 10 (Tcl) or 20 (Rust) runs over two rounds.
  Run-to-run noise on this shared machine was about 10% to 20%; a ratio near 1.0 means "no difference".
* zlib is one C call, so Tcl, compiled Tcl and Rust all run at libz speed (70 to 90 MB/s compress, 600 to 700 MB/s decompress). A repeat with 40 runs each showed
  15.1 ms (interpreter) against 15.0 ms (compiled) for compress. The 0.78x above is noise. Tcl's output was 99,789 bytes and libz's 99,485 (same level 6): a
  different zlib build or settings; not investigated.
* The Rust "coroutine" row is a plain enum state machine (no coroutines are needed natively), so it shows the cost of Tcl's coroutine machinery, not an
  equivalent mechanism.
* The Rust frame-split numbers are the same code for "scan" and "index" because natively there is no difference.
* AES: the table row is the 64 KiB run. The full **1 MiB** run (`aes_full.tcl`; `COMPILED=1` for the compiled one) took **158.5 s interpreted (6.6 kB/s)** and **44.5 s compiled
  (23.6 kB/s)**, both byte-identical to `openssl enc -aes-128-cfb8`. That is 135 us per byte interpreted and 42 us per byte compiled, because CFB8 needs one
  full AES block per byte. Rust: 6.6 MB/s in portable software, **57.8 MB/s with AES-NI encrypt** (serial: each byte depends on the previous ciphertext
  byte) and **515 MB/s with AES-NI decrypt** (ciphertext is known up front, so four blocks run in flight).

#### Players one core can serve (gateway work only, 20 TPS => 50 ms budget per tick)

Per player per tick: 5 inbound packets (frame split + position decode), 25 outbound frames (about 1000 B), AES-CFB8 over 1000 B out + 150 B in.

| variant | framing + decode | AES-CFB8 | total per player-tick | players per core (100% busy) | players per core (70% busy) |
|---|---|---|---|---|---|
| Tcl interpreter, pure-Tcl AES | 42.8 us | 154753.0 us | 154,795.8 us | 0.32 | 0.23 |
| Tcl + tcl-aot, pure-Tcl AES | 41.1 us | 47750.2 us | 47,791.3 us | 1.05 | 0.73 |
| Tcl interpreter, native AES (Rust AES-NI rates) | 42.8 us | 17.6 us | 60.4 us | 828 | 580 |
| Tcl + tcl-aot, native AES (Rust AES-NI rates) | 41.1 us | 17.6 us | 58.7 us | 852 | 596 |
| Rust, AES-NI | 0.5 us | 17.6 us | 18.1 us | 2,769 | 1,939 |

How these were computed, and why to treat them as optimistic:

* Per player per tick (20 TPS, 50 ms budget): 5 inbound packets of about 30 bytes (frame split + position decode), 25 outbound frames (about 1000 B, so
  about 20 KB/s), AES-CFB8 over 1000 B out (encrypt) and 150 B in (decrypt). Costs come from the measured per-operation times above.
* **Gateway work only**: no syscalls, no libpq, no `COPY` batching, no zlib, no scheduling, no GC or allocator pressure from many connections.
  Real numbers will be lower for every variant.
* The "native AES" rows are hypothetical: they assume a C binding doing AES-NI at the Rust rates and ignore the cost of crossing from Tcl to C per message.
  Pure Tcl AES is not an option: 0.3 to 1 player per core.
* In the Rust row, 17.6 us of the 18.1 us is AES-CFB8 encrypt. The serial encrypt is latency-bound; interleaving several connections' streams would hide that
  latency, so the Rust figure is conservative. The non-crypto part is 0.5 us in Rust and 41 to 43 us in Tcl: an 80x gap.

## Sockets (Tcl event loop sanity check)

```
cd tests/bench/tcl; ulimit -n 20000
PORT=25599 NCONN=900 DUR=10 out/gwshell sock_server.tcl &        # COMPILED=1 for tcl-aot; needs TCL_LIBRARY and TCLLIBPATH_EXTRA as above
sleep 1; PORT=25599 NCONN=900 python3 sock_client.py &          # server prints one SOCKET line after the 10 s window and exits
```

`sock_server.tcl` (`socket -server`, non-blocking binary channels, `fileevent readable`, `sock_parse` per read, one ack byte per aligned batch) against
`sock_client.py` (closed-loop clients, each sends a batch of 20 frames of 35 bytes and waits for the ack). Window: 10 s after all clients connect.

| setup | frames per second |
|---|---|
| **2000 clients, one Tcl process** | **crashes**: `*** bit out of range 0 - FD_SETSIZE on fd_set ***: terminated` |
| 900 clients, one process, interpreter | 523,886 |
| 900 clients, one process, tcl-aot | 797,527 (1.52x) |
| 2 processes x 900 clients (1800 connections), tcl-aot | 787,321 + 792,122 = 1,579,443 |

* **Hard limit:** Tcl 8.6's Unix notifier is built on `select()`. Any file descriptor at or above `FD_SETSIZE` (1024) aborts the process (glibc's fortified
  `FD_SET` check; without fortification it would corrupt memory). So one Tcl 8.6 process serves at most about 1000 connections, listener and other
  descriptors included. More players means more processes (Tcl 8.6 has no `-reuseport`, so separate ports or an external balancer) or a newer Tcl.
  This is a Tcl limit, not a tcl-aot one, but it is in the way for a "huge player count" design.
* The loop itself is healthy: about 800k small frames per second per process of pure parsing (about 8,000 players' worth of inbound at 100 packets per second
  each), with no outbound traffic, no encryption, and no database. tcl-aot's 1.5x here comes from compiling `sock_parse`, a loop over a list of integers.
* The Python client shares the 4 cores with the servers, so the two-process result is not an upper bound.
* Not measured: a Rust server for the same test.

## Where tcl-aot helped, and where it did not

Taken from `TBC_REPORT=1`, `TBC_DEADOPS=1` and `tbc::report` (regenerate with `TBC_REPORT=1 $TCLSH src/translate.tcl tests/bench/tcl/gw_procs.tcl /tmp/x.c Gw`).

| proc | speedup | why |
|---|---|---|
| `vi_decode_all` | **11.3x** | the hot loop is integer arithmetic over `lindex`; typed code covers it |
| `vi_encode_all` | 2.1x | the `lappend` per byte and the final `binary format` hand over to boxed code |
| `cfb8_encrypt` + tcllib `aes::*` | 3.2x to 3.6x | tcllib's AES is integer and list code; `::aes::MixColumns` 83% typed, `AddRoundKey` and `SubBytes` 100%; `EncryptBlock` itself only 6% typed (its `binary scan` and `unset` are hand-over points) |
| `split_scan`, `split_index` | 1.07x, 1.03x | the time is in `binary scan`, `string range` and list allocation, which are Tcl's own C code |
| `pos_decode_loop` | 1.13x | `binary scan ... QQQRRcu` is a hand-over point (only `c s S i I` with `*` is inlined); 68% of instructions typed but the scan dominates |
| `build_frames` | 1.04x | `binary format` is a hand-over point; the rest is `append` of byte arrays |
| `run_conns` / `conn_machine` | 1.07x | `yield` and the dynamic command `cn$c` are hand-over points; the report says 2000 calls (the coroutine bodies) "ran the interpreter's version because they were inside a coroutine or demoted" |
| `sock_parse` | 1.52x (in the socket test) | integer loop over a list |
| zlib | 1.0x | one C call |

### Observations for tcl-aot (not bugs in the output: every result matched the interpreter)

1. **`binary format` is not in `tbcPureBuiltins`** (`src/translate.tcl:82`; the list is `string list lindex llength lrange lsearch join split concat format
   lrepeat lreverse lreplace linsert encoding abs max min`). It reads no variables and runs no script, so a call to it should not end typed code. Both
   `vi_encode_all` and `build_frames` report `unsupported: invokeStk1 ::tcl::binary::format`.
2. **`binary scan` inlining covers only `c s S i I` (optional `u`) with count `*`** (`tbcScanFmt`, `src/translate.tcl:85`). Network protocols need big-endian
   doubles and floats (`Q`, `R`), and single values (`cu` without `*`, or with an `@offset`): `pos_decode_loop` and `split_scan` hand over at every scan.
   Those four or five format letters are most of what a Minecraft gateway does.
3. **Coroutines**: a proc that yields (`conn_machine`) ran the interpreter's version in this program, so the per-connection state machine gets no benefit.
   This is documented in `docs/usage.md`; it matters here because one coroutine per connection is the natural Tcl design.
4. **The module contains Tcl's own library procs** (`tclPkgUnknown`, `tcl::tm::*`, `tcl::clock::*`, `auto_load`, `tbcx::*`, ...): `TBC_CENSUS=1` lists 71
   procs, of which 13 are mine, 31 are tcllib's `aes`, and 27 come from Tcl's library because `init.tcl` has run before `procs.tcl` is sourced. It is
   harmless (2.7 MB of C, 34 s to compile at -O2) but a filter for "only procs defined by this file" would shrink modules.
5. **The static shell needs `TCL_LIBRARY`** (it embeds no `init.tcl`); without it the binary says "Can't find a usable init.tcl". A deployed gateway would have to
   ship the library directory or embed it. Documented, but easy to trip over.
6. Translation was fast (1.9 s) and I hit **no correctness problem**: all `RESULT` lines and the AES output matched in compiled mode.

## Conclusion

* **As the gateway for a Purpur-class target, Tcl + tcl-aot is not viable.** Even in the optimistic estimate it serves about 850 players per core when AES is
  done by a hypothetical native binding, against about 2,800 for Rust that is already AES-bound; for the non-crypto work the gap is 80x. With AES in Tcl it
  serves about one player per core. A single Tcl 8.6 process also cannot hold more than about 1000 sockets.
* **Crypto must be native**, whatever the language: pure-Tcl AES-CFB8 runs at 7 to 24 kB/s against 58 MB/s (encrypt) and 515 MB/s (decrypt) with AES-NI.
  The one-block-per-byte structure of CFB8 is what makes it so expensive, so a Tcl design would need at least a small C extension, which defeats the purpose
  of keeping the gateway tiny in Tcl.
* **tcl-aot does what it claims** on what it targets: 11x on a tight integer loop, 3.6x on tcllib's AES. Gateway code is not that shape. If its inlined
  `binary scan` and `binary format` covered `Q R` and single-value scans, the decode and build rows would probably move; I did not test that and did not modify
  tcl-aot.
* **What would change the answer:** a Tcl 9 or 8.7 notifier (epoll, no `FD_SETSIZE` limit), a native C binding for crypto and framing (at which point Tcl is
  only glue), or a much lower player-count target. For "hundreds of players, mostly idle", Tcl with native crypto would likely be enough; for "as many as
  possible", it is the wrong tool.
* **Caveats:** single machine, shared with the load generator; 10% to 20% noise; Rust code is a straightforward implementation, not tuned; the players-per-core
  numbers are estimates from microbenchmarks and ignore the system costs listed above; the Rust socket path was not measured.
