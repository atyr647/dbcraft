# Importing and exporting vanilla worlds

`tools/world_import.py` loads a vanilla 26.3 world (Anvil region files, `level.dat`, player files) into dbcraft's tables.  `tools/world_export.py` writes the tables
back as a world that the real vanilla server loads.  Both use only the Python standard library (`tools/world_import/anvil.py` is the NBT and region reader/writer);
nothing is downloaded and nothing from Mojang is committed (the test world is generated on demand and lives in `/tmp`).

## Usage

```
# import (libpq environment variables or DBCRAFT_PSQL select the database; the schema must be migrated and the reports loaded)
python3 tools/world_import.py /path/to/world [--replace] [--dimension minecraft:overworld] [--box CX1 CZ1 CX2 CZ2]
          [--jobs 4] [--no-level] [--no-players] [--player-names usercache.json] [--work DIR] [--limit N_REGION_FILES]
# export
python3 tools/world_export.py /path/to/new/world [--dimension ...] [--box ...] [--no-level] [--no-players]
```

`--replace` deletes the chunks the import overwrites (without it an existing chunk is an error).  The import runs in one transaction: either everything is
there or nothing.  The exporter prints the world seed; vanilla needs it as `level-seed` only for chunks that are not in the files.

26.3 world layout that both tools read and write: `level.dat`, `dimensions/minecraft/<dim>/region/r.X.Z.mca`, `players/data/<uuid>.dat`,
`data/minecraft/{world_gen_settings,world_clocks,weather,game_rules}.dat`.

## How the data is converted

Everything lands in the tables the world module already has, readable as rows (`docs/ARCHITECTURE.md`):

| Anvil | dbcraft |
|---|---|
| section `block_states` palette + packed longs | `mc.chunk_section.palette` (block state names, `minecraft:oak_log[axis=y]`), `bits`, `data` (wire format).  The on-disk longs are reused as they are when the width is 4 to 8 bits (disk and wire packing are the same: `floor(64/bits)` entries per long, none spanning); wider palettes become the global palette (16 bits) via `ref.block_state` |
| `biomes` | `biome_palette`, `biome_bits` (1 to 3 bits reused, else the 7-bit global palette), `biome_data` |
| `Heightmaps` (9-bit packed) | `mc.chunk.hm_*` as `smallint[256]` |
| `SkyLight` / `BlockLight` per section | `mc.chunk_light` (`kind` data / empty / NULL), see Light |
| `block_entities` | `mc.block_entity.nbt` = what the chunk packet carries (the update tag), `save_nbt` = the full save data (inventory, loot table, spawner settings; network-form NBT without `id`, `x`, `y`, `z`, `keepPacked`) |
| `level.dat` + `data/minecraft/*.dat` | seed, spawn, game and day time, weather, difficulty, game mode (`mc.world`, `mc.game_state`, `mc.dimension`, `mc.server_property`); game rules into `mc.game_rule` (`sql/700`; the game module does not read them yet) |
| `players/data/<uuid>.dat` | `mc.player` (position, rotation, health, food, game mode, XP) and the inventory rows; names from `usercache.json` next to the world |

26.3 formats the importer handles (found by reading real files, not documented anywhere): block-state palette entries are a mix of a bare string (the default
state), a `{"": name}` wrapper and `{id, properties}` with only the non-default properties; NBT lists may be heterogeneous with non-compound elements wrapped as
`{"": value}`; chunk files use zlib, gzip, none or LZ4 (the lz4-java block stream) and may be external `.mcc` files.

Light rule (derived by comparison with vanilla's packets): a file stores only layers that hold some light; vanilla's packet marks every other layer from the
lowest up to the highest lit one as `empty`; the importer does the same, and `mc.ensure_chunk_current` keeps imported light (it only recomputes when a chunk is dirty).

Block entity update tags follow `getUpdateTag` of each type (checked with `javap`): types without a custom tag send none; `saveCustomOnly` types drop an empty
`components`; banners keep it; vaults send `shared_data`; mob spawners send everything but `SpawnPotentials`.

## Measured

Test world: seed `dbcraft-import-7` generated by the real vanilla 26.3 server (`tools/world_import/vanilla_world.sh`), 780 chunks (10 region files, 18,720 sections, 387 block entities, 1 player).

| | time (4-core machine shared with other workers) |
|---|---|
| import, parse 1.8 to 2.3 s on 4 processes + load 1.2 to 1.5 s | 3.7 to 4.4 s = **about 11,000 to 13,000 chunks/min** |
| export | 3.3 to 6.2 s (about 125 to 240 chunks/s) |

(Counting non-air blocks in Python while parsing was the first fix: doing it in SQL afterwards cost 1.8 ms a section, 33 s for this world.  `mc.import_recount`
is kept for databases that load sections with `block_count = -1`.)

## Verification

1. **Chunk packets against the real server** (`tests/world_import/compare_chunks.py`, with a recording from `tools/world_import/capture_area.py` of vanilla running on
   the same files): 292 chunks compared component by component (heightmaps, every section, block entities, light).  **257 chunks are identical in every component.**
   The other 35 differ because their files still contain pending `PostProcessing` entries (vanilla updates those blocks when it loads the chunk: water, plants,
   fences) and the light next to them; `tests/world_import/check_postprocessing.py` confirms every differing chunk is in that set, none without.  The importer does not
   apply post-processing (see Gaps).
2. **Round trip through the files** (`tests/world_import/run.sh`): import, export, import the export again: chunk count, heightmaps, the block name of every cell of all
   18,720 sections, block counts and every block entity (including `save_nbt`) are identical (`digest.sql`).
3. **The real vanilla server on the export** (`VANILLA=1 tests/world_import/run.sh`, or by hand with `tests/world_import/verify_export.py`): 40 blocks were edited in
   dbcraft (gold, diamond, a chest and stairs with properties, an x-axis log, a hanging lantern, ...), the world exported and loaded by vanilla 26.3.  It starts without any
   error or data-fixer warning in its log; `/seed`, difficulty and the spawner and chest data match; **600 sampled positions (the 40 edited ones included) over all
   780 chunks answered `execute if block` exactly as the database says: 0 differ** (a negative control, a wrong block, answers `Test failed`).
4. **The real client on the imported world**: dbcraft's gateway served the imported world, the real 26.3 client joined as the imported player at its saved position
   (-5.5, 65, -7.5) and rendered vanilla's generated terrain (swamp with lily pads, trees, sand, water), hotbar from the imported inventory; the client log held only
   the baseline noise (Mojang account 401, Realms, OpenAL) and no protocol error.  Screenshot (not committed, Mojang textures): `/tmp/mc-client/shots/import-terrain.png`.
5. `tests/sql/700_world_import.sql` (section counts, recount, game rules, `save_nbt`) and `tests/world_import/test_anvil.py` (600 real chunks parse and write back
   byte-identically, malformed input fuzz, LZ4); the whole SQL suite stays green.

Without the generated world, `tests/world_import/run.sh` runs the unit tests and says it skipped the rest.

## What is and is not imported

Imported: blocks, biomes, heightmaps, light, block entities (with full save data), seed, spawn, time, weather, difficulty, game mode, game rules, players
(position, health, food, XP, game mode, inventory with item components).  Exported: the same, in the same layout.

Not imported (dropped; the export writes empty structures): entities in chunk files, structure starts and references, POI, scheduled block and fluid ticks, raids,
scoreboard, advancements, statistics, map data, boss bars, the wandering trader, random sequences.  Only the overworld exists in dbcraft, so the Nether and the End
are not imported.

## Gaps and limits

* Pending `PostProcessing` is not applied (35 of 292 chunks in the comparison).  Vanilla applies it itself when it loads the exported chunks only if the export keeps it;
  the exporter writes none, so the few water edges and plant blocks that were waiting stay as they are in the file.
* Light comes from the file.  Next to chunks with pending post-processing the light differs from what vanilla's packet sends after the update.
* Block entity update tags of `trial_spawner` (ominous state), brushable blocks, campfires, shelves and `potent_sulfur` follow `getUpdateTag` but were not seen in the test world.
* An exported world loses everything under "Not imported"; players keep their inventory but not advancements or statistics.
* Items in inventories are written from the jsonb `components`; unknown future components are passed through untouched.
